# RCA — chezdina.net still shows old catalog / old info after republish

## Problem statement
After redeploying, the live custom domain (chezdina.net/boutique, /console, /rider) keeps showing the OLD catalog (clothing products) and old business info, despite the preview catalog having been cleaned to 34 women's shoes/bags products and commit `9714d7f` (rider PWA manifest fix) being pushed.

## Answer to (1): Is the latest build serving? — YES, the newest build is live
- Active run: `55c2cca1-4963-49cd-a920-7a4bf9550fc7`, type=redeploy, status=**success**, completed **2026-10-10 03:16 UTC**. It is the deployment's `active_run_id` (i.e. promoted and serving).
- Build (`build_image`) **SUCCEEDED** at 2026-10-10 03:15 and produced image `sha256:aab17bca…a295d`, which is the image the active run is running — so the code currently live IS this latest build.
- Frontend type = **cloudflare** (static files served from R2 by a Cloudflare worker; R2 is refreshed at build time). `GET /` and `GET /rider` both return **200** with the current app HTML (theme-color `#b02a2a`, dynamic manifest), not a stale nginx/placeholder page.
- Conclusion: this is NOT a CDN/cache problem and NOT a stale-build problem. The republish did reach production. (Note: the probe tool targets the default host `dina-boutique.emergent.host`; both custom domains `chezdina.net` and `www.chezdina.net` are verified and are served by the same Cloudflare worker off the same R2 build, so they serve the identical latest bundle.)

## Answer to (2): Does production MongoDB still hold the old catalog? — YES (root cause)
Read-only queries against the **production** database (name bound in prod: **`dina-boutique-dina_store`**) on the active run:
- **products count = 120** (preview = 34).
- **distinct categories = [Accessoires, Chaussures, Ensembles, Hauts, Jupes, Pantalons, Robes, Sacs]** — includes clothing (Robes/Hauts/Jupes/Pantalons/Ensembles).
- **79 of the 120 products are clothing** (`category ∈ {Robes, Hauts, Jupes, Pantalons, Ensembles}`). Preview was supposed to contain only shoes/bags.
- **site_settings** still holds old/test content: hero subtitle "Chaussures, robes, sacs et accessoires…", `documents.receipt_footer = "TEST_footer waved"`, test integration tokens (`SECRETTOKEN123456`, `META-PX-1`, `TT-PX-1`), etc.

So production Mongo (`dina-boutique-dina_store`) is a **different, un-synced database** from preview and still contains the full old catalog + old settings.

## Root cause
The product catalog and business info are **data stored server-side in the production MongoDB**, not baked into the code. The preview cleanup (down to 34 shoes/bags) was performed by DB scripts against the **PREVIEW** database only. Redeploys rebuild and roll out code **but never migrate data** (only an *initial* deploy provisions + migrates preview→prod). Additionally, backend `seed_if_empty` only inserts into **empty** collections, so a prod `products` collection that already has 120 docs is left untouched. Result: the latest code is live, but it reads the old prod data → old clothing + old info appear.

## What is needed to sync (no data was modified by this investigation)
The fix is a **production-data** operation; it cannot be fixed by another republish:
1. Apply the same catalog cleanup to the PRODUCTION DB `dina-boutique-dina_store` — either run the cleanup/seed scripts against production, or use the Deployment Panel → Database (DB Manager) to sync the cleaned `products` and `site_settings` from preview to production.
2. **Caution:** do NOT blindly copy the entire preview DB over production — production also holds live `orders`, `customers`, `invoices`, etc. Sync selectively (`products`, `site_settings`/`business`) so real transactional data is preserved.
